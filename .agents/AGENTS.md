# Agent Instructions

## Git Commit and Push Policy
- **CRITICAL RULE**: Do NOT commit or push changes to Git on your own.
- Only run `git commit` or `git push` when the user explicitly requests it.

## Quy tắc Git Commit và Push
- **QUY TẮC QUAN TRỌNG**: KHÔNG tự ý thực hiện commit hoặc push mã nguồn lên Git.
- Chỉ thực hiện `git commit` hoặc `git push` khi người dùng yêu cầu rõ ràng.

## Protocol Security and Encryption Policy
- **SIP Protocol**: Must always run over UDP or TCP (plain unencrypted SIP, no TLS/SIPS).
- **HTTP/2 Protocol**: Must always be unencrypted HTTP/2 Cleartext (h2c, no TLS/HTTPS).
- **RTP Protocol**: Audio and video media streams must always run over plain RTP (unencrypted RTP, no SRTP/encryption).

## Quy chuẩn Bảo mật và Mã hóa Giao thức
- **Giao thức SIP**: Luôn luôn chạy trên nền UDP hoặc TCP (SIP thường không mã hóa, không sử dụng TLS/SIPS).
- **Giao thức HTTP/2**: Luôn luôn chạy dạng không mã hóa HTTP/2 Cleartext (h2c, không sử dụng TLS/HTTPS).
- **Giao thức RTP**: Các luồng truyền thông audio và video phải luôn luôn chạy trên RTP thường không mã hóa (không sử dụng SRTP/mã hóa).

## SIP and RTP Protocol Rules for Android App
- **SIP Protocol**: Must run over unencrypted UDP or TCP. For registration and calls, prioritize/use TCP instead of UDP due to large SIP message sizes to avoid IP fragmentation issues.
- **RTP Protocol**: Audio media streams must strictly use the **PCMA** codec. Video media streams must strictly use the **H264** codec. Both streams must be transmitted over plain unencrypted UDP (no SRTP).

## Quy tắc giao thức SIP và RTP cho ứng dụng Android
- **Giao thức SIP**: Bắt buộc chạy trên UDP hoặc TCP không mã hóa. Đối với đăng ký và gọi, hãy ưu tiên/sử dụng TCP thay vì UDP do độ dài bản tin SIP lớn nhằm tránh hiện tượng phân mảnh IP.
- **Giao thức RTP**: Luồng âm thanh (Audio) bắt buộc phải sử dụng mã hóa **PCMA**. Luồng hình ảnh (Video) bắt buộc phải sử dụng mã hóa **H264**. Cả hai luồng phải truyền tải trên UDP thường không mã hóa (không sử dụng SRTP).

## 3GPP & GSMA PROTOCOL CONSTRAINTS (TS 26.114, TS 24.186, TS 29.175, TS 29.176 & NG.134, TS.66)

### 1. Architectural & Environment Scope
*   **Offline Air-Gapped Target**: System is deployed offline on RHEL/K8s. Erlang core (`erlang-sip` utilizing ETS tables) and Go components (`go-mf` with vendor dependencies) must not use external network fetch or package installs.
*   **SBA Internal Trusted Subnet**: All Service-Based Architecture (SBA) APIs run on HTTP/2 Cleartext (h2c) without TLS.
*   **No DC Multiplexing**: Currently, the system operates in standard **1-1 transmission mode** (one SCTP association per 'm=application' line). Disregard `g.3gpp.dc-mux` attributes or multi-app mappings.

### 2. DC1 Interface Rules (3GPP TS 29.175 Compliance - IMS-AS <-> DCSF)
All SBA transactions on the DC1 interface must match the OpenAPI YAML 'TS29175_Nimsas_SessionEventControl.yaml' and 'TS29175_Nimsas_MediaControl.yaml'.
*   **HTTP/2 h2c Transport**: Go HTTP Clients for DCSF/IMS-AS MUST enforce HTTP/2 Cleartext via `http2.Transport{ AllowHTTP: true }`.
*   **Trailing Slash Routing**: DCSF router MUST register both `/session-event-subscriptions` and `/session-event-subscriptions/` endpoints to prevent 301 redirection / 405 Method Not Allowed failures on POST.
*   **SBA Error Formatting**: Any 4xx/5xx response generated by DCSF or IMS-AS MUST use `Content-Type: application/problem+json` and wrap errors inside the 3GPP standard `ProblemDetails` JSON schema.
*   **SIP Session Release & Memory Cleanup**: Upon SIP BYE, SIP CANCEL, or any call establishment failure (SIP response >= 300), the IMS-AS Call FSM MUST send `DELETE /session-event-subscriptions/{subscriptionId}` to the DCSF to release state and prevent memory leaks.
*   **3GPP PS Data Off Support (Rel-19)**: IMS-AS must detect `+g.3gpp.ps-data-off` in SIP REGISTER and propagate `"psDataOff": "ACTIVE" / "INACTIVE"` in the `SessionEventNotification` payload.

### 3. DC2 Interface Rules (3GPP TS 29.176 Compliance - IMS-AS <-> Media Function / MF)
All media plane control transactions must match the 'TS29176_Nmf_MRM.yaml' OpenAPI specification.
*   **HTTP PATCH (RFC 6902 JSON Patch)**: When updating media context resources, the IMS-AS MUST use the HTTP PATCH method with `Content-Type: application/json-patch+json`. The payload must be an array of `PatchItem` objects (supporting "add", "remove", "replace").
*   **Immutability Constraints**: Once WebRTC handshakes have started, the parameters `localMbEndpoint`, `remoteMbEndpoint`, `localDcEndpoint`, and `mediaProcessingURL` are **immutable**. Any PATCH request trying to modify these must be blocked by the MF with `403 Forbidden` carrying application error `"MEDIA_CONNECTION_CHANGED"`.
*   **Bootstrap vs. Application Data Channels**:
    *   **BDC (Bootstrap DC)**: `mediaProxyConfig` MUST be strictly set to `"HTTP_PROXY"`. The creation request must include `mdc1Info` pointing to the DCSF.
    *   **ADC (Application DC)**: `mediaProxyConfig` can be `"UDP_PROXY"` (transparent raw packet forwarding to DC AS) or `"HTTP_PROXY"`. If `"UDP_PROXY"` is selected, encryption attributes like `tlsId`, `sctpPort`, or `fingerprint` MUST NOT be populated inside the `MdcEndpoint` structure.
*   **Dynamic Termination Allocation**: Upon receiving `POST /contexts` with an empty `terminationId` `""`, the MF must dynamically allocate a unique string and return it in the response. Hardcoding IDs is prohibited.

### 4. Signaling Plane & SDP Rules (3GPP TS 26.114 Compliance - Gm Interface)
All SDP offers/answers generated by the client (`uesim`) or modified by the IMS-AS (`imsas`) must follow TS 26.114 Section 6.2.10.
*   **SDP Media Line Ordering**: The data channel description (`m=application`) MUST be positioned **strictly after** the first speech/audio (`m=audio`) line. Senders and receivers must strictly enforce this order.
*   **Prohibited Media Attributes**: Directional attributes `a=sendonly` and `a=recvonly` are undefined and strictly prohibited under the `m=application` block. Only `a=sendrecv` (or omitted) and `a=inactive` are allowed.
*   **MMTel Hold & Resume**: Placing a call on HOLD must translate to `a=inactive` on the `m=application` line. Resuming must switch back to `a=sendrecv`.
*   **Stream ID Partitioning**:
    *   **Stream ID < 1000**: Reserved strictly for BDC (subprotocol "http").
        *   Stream ID `0`: Local Network Provider
        *   Stream ID `10`: Local User
        *   Stream ID `100`: Remote Network Provider
        *   Stream ID `110`: Remote User
        *   **No `a=3gpp-req-app` attribute is allowed on BDC media lines**.
    *   **Stream ID >= 1000**: Reserved strictly for ADC.
        *   Must include `a=3gpp-req-app:<req-app-id>;<stream-id>-<endpoint-type>` where endpoint-type is 'UE' or 'Server'.
*   **SBA Connection Failure Fallback (TS 24.186 Clause 9.4.4)**: If communication over the DC1 interface fails or times out during session establishment, the IMS-AS **MUST NOT** drop the entire SIP session. It must set the SCTP data channel port to `0` in the outgoing offer/answer, and continue establishing the primary MMTel audio/video streams (VoLTE/RTP) normally.

### 5. User Plane Protocol Stack Rules (MF User Plane Engine)
*   **CRC32c Checksum Enforcement**: The SCTP user plane engine MUST strictly use the CRC32c (Castagnoli) algorithm [RFC 4960] for calculating and verifying checksums. The legacy Adler32 checksum is prohibited. Discard invalid checksum packets silently.
*   **SCTP Stream Reconfiguration (RFC 6525 / RFC 8831)**: When an application data channel is closed, the MF must perform an "Outgoing SSN Reset Request" to reset stream states, rather than tearing down the entire DTLS association.

### 6. Client-Side WebView & API Rules (GSMA TS.66 Compliance)
*   **Strict MIME Type Check**: The Android client / WebView sandbox MUST perform strict MIME type validation for resources downloaded over BDC. Extensions `.html`, `.js`, `.css`, and `.zip` must match their respective content types. Mismatches must raise an exception and block execution.
*   **Container Lifecycle Bound**: The browser-like container lifecycle must be tightly bound to the active voice session. Dialer-initiated call termination must invoke the JavaScript API to trigger memory cleanup of JS peer connection and data channel objects.

### 7. Code Refactoring Code of Conduct
*   Every bug fix or structural update must be validated against these rules.
*   If a proposed fix violates any schema or protocol mapping mentioned above, search for alternative compliant implementations.
*   Do not replace standard JSON schemas with arbitrary key-value objects. Keep types strictly mapped (e.g., float/number representations in QoS, exact enum matches).

### 8. Transport Layer Isolation & JSEP/SIP SDP Guardrails
*   **BDC & ADC Isolation**: BDC and ADC sessions MUST execute on separate WebRTC PeerConnection instances (`bdcPC` and `adcPC` / `bdcPC` and `adcPC`). The system does not support the WebRTC BUNDLE grouping attribute (`a=group:BUNDLE` across audio/video/data is prohibited).
*   **Port & Crypto Allocation**: Each data session (BDC and individual ADCs) MUST negotiate on independent UDP ports on the Mb interface (Media Function). Each PeerConnection must generate its own self-signed certificate, resulting in distinct `a=fingerprint` and `a=tls-id` lines in the respective media blocks.
*   **JSEP Local Descriptions vs. Over-The-Air (OTA) SIP SDP Separation**:
    *   **JSEP Local Descriptions**: Local SDP generated by calling `createOffer()` or `createAnswer()` on an isolated PeerConnection (such as `adcPC`) is a single-m-line fragment representing only that transport. You MUST NOT add audio tracks, video tracks, or BDC streams to the `adcPC` instance. You MUST ONLY pass a single-m-line SDP fragment matching the specific connection context to `setLocalDescription()` and `setRemoteDescription()`.
    *   **OTA SIP Descriptions**: All SDP bodies encapsulated within SIP INVITE, re-INVITE, UPDATE, or responses (183, 200 OK) MUST be cumulative. The outbound SIP SDP Offer/Answer must contain the conversational speech `m=audio` block, conversational `m=video` block (if active), BDC `m=application` block, and the newly negotiated ADC `m=application` block. Sending an OTA SIP SDP containing only the `m=application` of the ADC (without `m=audio` and BDC) is a critical violation and MUST be blocked.
*   **SDP Transformation Enforcement**:
    *   **SDP Merging (Uplink)**: When sending a SIP re-INVITE to establish an ADC, the SIP UA MUST programmatically extract the ADC media description from the local `adcPC` offer and merge/append it into the active multi-m-line SIP SDP body using the helper function `MergeAdcOffer`.
    *   **SDP Splitting (Downlink)**: When receiving a multi-m-line SDP Answer from the network, the SIP UA MUST programmatically split/extract the specific `m=application` block belonging to the ADC (using `a=3gpp-req-app` containing the unique `appId` match) and feed ONLY that extracted 1-line fragment into `adcPC.setRemoteDescription()` using the helper function `SplitAdcAnswer`.
*   **Fallback & BDC Stream Preservation**: When modifying the session (e.g., closing a Mini-App or SBA fallback), the SIP UA must rewrite the SDP to target ONLY the second `m=application` block (ADC) to set its port to 0. The first `m=application` block (BDC) and VoLTE streams must remain active (port > 0) throughout the voice call.

## BDC & ADC LIFECYCLE & SIGNALING (3GPP/GSMA ADVANCED RULES)

### 9. BDC PERSISTENT LIFECYCLE RULE (3GPP TS 24.186 Clause 9.3.2.1.5)
- **BDC Setup**: The Bootstrap Data Channel (Stream ID < 1000, subprotocol="http") MUST be negotiated and established during the initial call setup phase (SIP INVITE/200 OK) alongside the primary voice/video streams.
- **Persistent BDC**: Once the BDC DTLS/SCTP association is established, it MUST remain active and available for the entire duration of the IMS session.
- **Modification Guard**: Under NO circumstances shall the SIP UA or IMS-AS close, disable, or remove the BDC m-line description during any subsequent SIP session modification procedures (re-INVITE or UPDATE for adding/removing ADCs). Setting the BDC port to 0 during active calls is strictly prohibited.
- **Teardown**: The BDC must only be released and torn down when the primary SIP session is terminated (upon receiving or sending a SIP BYE or CANCEL).

### 10. APP SELECTION & BOOTSTRAPPING FLOW (3GPP TS 26.114 Clause 8.1.1)
- **Root-App Load**: Upon successful BDC establishment, the client MUST automatically trigger an HTTP GET request for the root ("/") URL over the BDC stream to fetch the main service menu (Root Application).
- **Mini-App Download**: When the user clicks a menu item representing a specific service, the client MUST execute subsequent HTTP GET requests over the active BDC stream to download the targeted Mini-App package (HTML5, JS, CSS, or ZIP package) to the WebView runtime. This download action MUST NOT trigger any SIP signaling messages.

### 11. ON-DEMAND ADC SIGNALING TRIGGER (GSMA NG.134 Clause 4.2.4)
- **JS Triggering**: After the Mini-App is loaded and executed inside the client sandbox, the application JavaScript logic will call 'createDataChannel()' to request data connectivity.
- **SIP re-INVITE for ADC**: This JS invocation MUST natively trigger the client signaller (SIP UA) to initiate a SIP re-INVITE or UPDATE request carrying a cumulative SDP Offer.
- **Cumulative SDP Offer**: The SDP offer generated for ADC establishment MUST contain:
  1. The active conversational voice/speech 'm=audio' block.
  2. The active BDC 'm=application' block.
  3. A brand-new 'm=application' block representing the ADC (Stream ID >= 1000) containing the required 'a=dcmap', 'a=3gpp-req-app', and optional 'a=3gpp-qos-hint' attributes.
- **Uplink/Downlink Separation**: Enforce the SDP Merging (on outgoing) and SDP Splitting (on incoming) logic to ensure the WebRTC PeerConnection for the ADC ('adcPC') only processes its dedicated 1-line SDP fragment.

### 12. MINI-APP TERMINATION & ADC RELEASE (3GPP TS 24.186 Clause 9.3.2.1.4)
- **Exit Detection**: When the user exits the Mini-App (e.g., clicking 'Back' or returning to the Root-App menu list), the client WebView MUST notify the native Android bridge.
- **SIP re-INVITE for Release**: The SIP UA MUST immediately generate a subsequent SIP re-INVITE or UPDATE containing an updated SDP offer to release the ADC.
- **ADC Port Zeroing**: In the SDP offer, the client MUST set the UDP port number of the specific ADC's 'm=application' block to 0 (or remove the corresponding 'a=dcmap' line if other ADCs remain on that m-line).
- **User Plane Clean-up**: Upon successful completion of this re-INVITE (200 OK), the Media Function (MF) and the client MUST release the physical network resources and close the user plane sockets associated with that ADC. The BDC connection MUST remain untouched.

### 13. INITIAL STANDALONE DATA CHANNEL BAN (GSMA NG.134 & TS.66 Clause 4.3)
- **Call Pre-Requisite**: Standalone data channel sessions (SDP offers containing only data channels without MMTel speech/video) are strictly prohibited during initial INVITE.
- **Client Guard**: The client SDP generator ('createOffer') MUST raise an exception and block execution if no speech/video media has been established prior to the data media request.
- **Server Guard**: If the terminating server receives an initial INVITE containing only 'm=application' media, it MUST reject the transaction immediately with a SIP 488 (Not Acceptable Here) or SIP 606 (Not Acceptable) response.
